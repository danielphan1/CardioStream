**LD-1 — FilterStateBlock renders LINE-level pills, not facet-level pills.**
The brief (§6) asks for a ribbon of five facet pills and supplies its own escape
hatch: "If a ribbon cannot hold all of that, keep the sentences and restyle their
typography only. The contract outranks the visual." It cannot hold it.
Three independent assertions break, and the citation matters, so here it is
precisely:
- `FilterStateBlock.test.tsx:92` and `:158` assert the exact filter sentence
  ("All data · All times of day · All categories · All pulse categories" and the
  30-day variant) through `getByText`. Testing Library's `getNodeText` joins only
  the DIRECT text-node children of an element, so the moment that sentence is
  split across child `<span>`s the element's matched text becomes `""` and both
  assertions fail. The filter sentence is precisely the one the brief wants cut
  into four facet pills.
- `:57` asserts `querySelectorAll("p")` has length 3, which a five-pill ribbon
  breaks the moment a pill is a paragraph.
- `:110` compares each `p.textContent` to the exact sentence. **Correction to the
  first draft of this plan, which cited `:110` for the `getNodeText` mechanic:
  that was wrong — `textContent` DOES include descendant spans, so `:110` would
  survive the split on that mechanic alone.** It breaks for a different reason:
  the " · " separators cease to be text when interpuncts become pill boundaries.
  The argument does not rest on it either way.

These are not assertions about old markup — they are the enforcement of the
contract clause "the sentences' text content stays derivable from
`buildFilterSentence` / `buildShowSentence`". Therefore: each of the three
EXISTING `<p>` elements becomes its own pill (`rounded-full`, hairline, mist
fill, ≥18px, one aria-hidden lucide icon) with its full sentence kept as a single
direct text node. That delivers the pill vocabulary and the ribbon read without
forking the copy, without duplicating a fact, and `FilterStateBlock.test.tsx`
passes completely unchanged. Do not split a sentence. Do not add a second home
for any fact.

**LD-2 — the chart swap is single-layer sequential, and THE REMOUNT BOUNDARY
MOVES INSIDE `FadeSwap`.** Keeping the outgoing chart mounted alongside the
incoming one would mount a second Recharts `ResponsiveContainer` and risk the
documented zero-width measurement failure, so the swap is sequential: the
outgoing node drifts out, then the incoming node crests in.

The structural catch, and the reason this decision is written out: today
`ChartDeck.tsx:167` is `<div key={key}><FadeSwap>{body}</FadeSwap></div>`. The
key sits on the WRAPPER, so every `chartView` change unmounts that div and
destroys `FadeSwap` with it. A `swapKey` prop bolted onto that structure could
never be observed — the component instance is replaced, not updated — and the
delivered result would be entrance-only with no exit at all. So:

- `ChartDeck` renders `<FadeSwap swapKey={key} direction={direction}>{body}</FadeSwap>`
  and the wrapper div keeps ONLY its height class. **The `key` comes off the
  wrapper.**
- `FadeSwap` holds `committed: { key, node }` in state, seeded from the first
  render so there is no exit on mount, and renders it as
  **`<Fragment key={committed.key}>{node}</Fragment>`** — import `Fragment` from
  `react`. The key preserves the fresh-mount guarantee Recharts needs (the whole
  reason the key exists at all) while letting the `FadeSwap` instance survive
  the swap.
  **IT MUST BE A FRAGMENT, NOT A DIV, AND NO AUTOMATED GATE CAN TELL YOU
  OTHERWISE.** The height chain today is
  `<div className="h-[clamp(...)]">` → FadeSwap's own `h-full w-full` div
  (line 63) → `CombinedTimeline` → `ResponsiveContainer`, unbroken `h-full` the
  whole way. You cannot put the key on FadeSwap's existing `h-full w-full` div:
  that div carries the transition classes, the shown/hidden state and
  `data-swap-phase`, so keying it would remount it and destroy the very
  transition this work exists to create. A new inner node is therefore forced —
  and an inner `<div key={committed.key}>` has AUTO height, which breaks the
  chain, makes `ResponsiveContainer` measure 0 and renders the timeline blank.
  That is the documented Pitfall 2, and Recharts draws nothing under jsdom, so
  the suite stays green while the chart is empty in the browser. A keyed
  Fragment forces the remount while adding no DOM node and no height link. If
  you have a reason to prefer a div, it MUST carry `h-full w-full` — but prefer
  the Fragment.
- While `swapKey === committed.key` it renders the LIVE `props.children` under
  that internal key, not the stored node. This matters: a date-filter change
  does not alter `key`, and a frozen stale node would be a data bug, not a
  motion bug.
- `direction` is 0 whenever the swap was not a view change (a dataset toggle
  also changes `key`). Direction 0 commits immediately and runs the entrance
  only — exactly today's behaviour, unchanged. Only a real view swap
  (direction ±1) gets the exit phase.
- `FadeSwap` exposes `data-swap-phase` on its wrapper: `exit` while the outgoing
  node drifts out, `in` once the incoming node has crested. This is the only
  thing that makes the exit phase OBSERVABLE, and Task 3 adds a ChartDeck test
  that asserts it. A grep for a `direction` identifier passes on an
  entrance-only build; that test does not.
- THE EXIT→COMMIT HANDOFF IS A TIMER, AND `transitionend` IS FORBIDDEN (A-10).
  jsdom never fires `transitionend`, so a `transitionend`-driven commit would
  hang the new `data-swap-phase="in"` `waitFor` and fail the suite while the
  browser behaved perfectly — the worst class of gate failure, one that blames
  the wrong thing. Use a `setTimeout` matching `--dur-state` (220ms) inside an
  effect, with the existing double-rAF for the entrance. That is the precedent
  already in this component.
- INTERRUPTION MID-EXIT must not strand the chart (A-9). A second `swapKey`
  change while `phase === "exit"` can otherwise fire a pending commit holding a
  stale captured key — chart B flashes in and straight back out — or leave the
  wrapper parked at opacity 0, and a permanently blank chart on a health
  dashboard is the worst outcome in this plan. Two rules: key the exit effect on
  `swapKey` so React's cleanup cancels the superseded timer, and commit from the
  CURRENT props at fire time rather than from a value captured when the timer
  was armed. This is a correctness concern, not a brief requirement.

The existing suite stays green without edits: `ChartDeck.test.tsx` always calls
`useFilters.setState` BEFORE `render`, so no already-mounted deck sees a view
change in any current test and no existing assertion becomes async.

**LD-3 — press feedback is an unlayered `.press-swell` class in `index.css`.**
Tailwind v4 emits its utilities inside cascade layers; unlayered CSS beats
layered CSS regardless of source order, so a plain `.press-swell` rule always wins and
cannot be half-copied at a call site. Each button gains one class, the
`motion-reduce` companion lives in exactly one place, and grep gate 5 stays clean
because no new Tailwind `transition-*` class is introduced by this item. The name
is `press-swell`, not `press`, for one concrete reason: four files already use
the WORD "press" in prose and every toggle in the app carries `aria-pressed`, so
a bare `press` cannot be grep-verified. `press-swell` has zero collisions in the
repo today — verified at planning time — which is what makes the coverage gate in
Task 1 exact rather than approximate.
