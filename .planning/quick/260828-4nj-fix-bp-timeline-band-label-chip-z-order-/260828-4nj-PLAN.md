<objective>
Fix the BP Timeline band-label chip z-order regression identified in the 2026-08-28T10-00-16Z
impeccable critique (P1): the chip fix that shipped in commit `852e0a9` (quick task 260828-2l6)
does not work -- band-label chips for Hypotension, Normal, Stage 2, and Hypertensive Crisis render
UNDERNEATH the plotted systolic/diastolic lines, not above them, making the labels harder to read
than the original bare-text version they replaced.

Root cause (confirmed by reading the installed Recharts 3.9 source,
`frontend/node_modules/recharts/es6/cartesian/ReferenceArea.js`): `ReferenceArea` wraps its ENTIRE
render -- the background rect AND whatever is passed via its `label` prop -- in a single
`<ZIndexLayer zIndex={props.zIndex}>`, defaulting to `DefaultZIndexes.area` (100), one layer below
`Line`'s `DefaultZIndexes.line` (400). A custom function passed via `label` is never promoted to
Recharts' `label` zIndex layer (2000) -- that promotion only happens for a real `<Label>`/
`<LabelList>` element used as a direct chart child, not for content nested inside a `ReferenceArea`'s
own `label` prop. The current top-of-file doc comment and the `makeBandLabelChip` JSDoc (both added
in commit `852e0a9`) claim otherwise -- both claims are factually wrong and must be corrected as
part of this fix, not left standing.

This was independently re-verified in this planning session: a live Playwright inspection of
`svg.recharts-surface > g[class*="zIndex-layer"]` against the running dev server (localhost:5173,
default "All data" view) shows the four chip text nodes and their background rects living inside
`recharts-zIndex-layer_100` -- the SAME layer group as the six band-tint backgrounds -- which
appears in the DOM BEFORE `recharts-zIndex-layer_400` (2 `.recharts-line` paths). A captured
screenshot at that state visually confirms the systolic/diastolic lines painting over the
"Hypertensive Crisis," "Stage 2," "Normal," and "Hypotension" chips exactly as the critique
describes.

The fix: split each of the four labeled bands into two sibling `<ReferenceArea>` elements sharing
identical `y1`/`y2` -- one keeps the background tint with no label (`zIndex` left at its default
100, unchanged visual tint behavior), the other is an invisible label-only host
(`fill="transparent"`, `stroke="none"`) given an explicit `zIndex={DefaultZIndexes.axis}` (500,
imported directly from the `recharts` package, confirmed exported from `recharts/es6/index.js` and
therefore from the `recharts` package root) so it renders in a zIndex layer that paints strictly
after -- and therefore visually above -- `Line`'s 400 layer. `ReferenceArea`'s `zIndex` prop is a
real, typed (`zIndex?: number`), pass-through prop (`recharts/types/cartesian/ReferenceArea.d.ts`),
not a hardcoded internal value -- confirmed in source, not assumed from docs.

Purpose: the BP Timeline is the app's default, highest-stakes hero chart -- the first glanceable
read of Chris's own BP trend -- and this is the second attempt at making its band labels legible.
This plan's entire point is verifying the fix against the live DOM and a live screenshot before
declaring it done, exactly the step the prior fix (852e0a9) skipped.

Output: an updated `BPTimeline.tsx` where the four labeled bands each render as two ReferenceAreas
(tint + label host), corrected doc comments describing the real Recharts zIndex mechanism, and
live-verified DOM/screenshot evidence that the chips no longer render underneath the plotted lines.
</objective>
