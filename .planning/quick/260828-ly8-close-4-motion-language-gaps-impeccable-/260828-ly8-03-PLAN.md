## Design decision: the fade lives entirely inside DateRangePicker.tsx, not FilterBar.tsx

FilterBar.tsx owns the `customOpen` boolean and the `{customOpen && <div className={`mt-4${pulseClass("dateRange")}`}><DateRangePicker .../></div>}` wrapper -- that wrapping div ALSO carries the
D-08 agent-pulse ring-highlight class (`pulseClass("dateRange")`), which this plan must not disturb.
Rather than adding a second wrapper div in FilterBar.tsx (which would need to coordinate two
independent class-toggling mechanisms on nested elements), this plan puts the fade entirely on
DateRangePicker's OWN root div (currently `<div className="flex flex-col gap-4">`, wrapping the
From/To inputs, the DayPicker calendar, and the Apply button). Because FilterBar's `customOpen &&`
conditional already fully unmounts DateRangePicker on close and mounts a brand-new instance on
reopen, DateRangePicker's own `useState(false)` for the fade always starts fresh on every open --
no key, no reset effect, no coordination with FilterBar needed. FilterBar.tsx is NOT modified by this
plan.

## The double-rAF idiom to mirror (read `ChartDeck.tsx`'s `FadeSwap` function directly)

`ChartDeck.tsx` (lines ~93-123) defines a `FadeSwap` wrapper: `useState(false)` for `shown`, a
`useEffect(() => { ... }, [])` that schedules an outer `requestAnimationFrame` whose callback
schedules an inner `requestAnimationFrame` that calls `setShown(true)`, with cleanup cancelling both
via `cancelAnimationFrame`. The comment above it explains why: "Double rAF guarantees the initial
styles are painted before the toggle so the transition actually runs." This plan reuses that exact
technique, adapted to DateRangePicker's own state (an unconditional entrance, not a keyed swap) --
same shape, not a new invention.
