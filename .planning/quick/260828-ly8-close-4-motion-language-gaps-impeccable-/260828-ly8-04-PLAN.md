## The double-rAF FadeSwap idiom to mirror (read `ChartDeck.tsx`'s `FadeSwap` function directly)

`ChartDeck.tsx` (lines ~93-123) defines: `useState(false)` for `shown`; a `useEffect(() => { ... },
[])` that schedules an outer `requestAnimationFrame` whose callback schedules an inner
`requestAnimationFrame` that calls `setShown(true)`, with cleanup cancelling both via
`cancelAnimationFrame`; and a returned wrapper `<div>` whose className is a template literal:
base classes + `transition-[opacity,transform] duration-[250ms] ease-in-out motion-reduce:transition-none` (unconditional) + a conditional `${shown ? "scale-100 opacity-100" : "scale-95 opacity-0"}`.
ChartDeck then uses it as `<div key={active.id} className="h-[420px]"><FadeSwap>{active.hero(data)}</FadeSwap></div>` -- the KEY lives on the outer wrapping div (forcing a full subtree remount, which
resets FadeSwap's own `shown` state back to `false` so the entrance replays), while `FadeSwap` itself
carries no key and needs none, since it's remounted along with everything else inside the keyed
parent.

This plan reuses that exact same two-part shape (keyed outer div + unkeyed `FadeSwap` inside it) for
AddRecordPage's Lab/Incident/Procedure swap. Keep `FadeSwap` LOCAL to AddRecordPage.tsx (module-level
function, not exported, not imported from ChartDeck.tsx) -- do not modify ChartDeck.tsx or extract a
shared module. Two independent, near-identical `FadeSwap` implementations across the codebase is an
acceptable, deliberate tradeoff here: it keeps this plan's file ownership limited to AddRecordPage.tsx
(this quick task's plans run in isolated worktrees with exclusive file ownership; touching
ChartDeck.tsx would create an unnecessary cross-plan dependency for zero behavioral benefit). One
sizing difference from ChartDeck's version: DROP the `h-full w-full` classes ChartDeck's `FadeSwap`
carries (those exist to fill ChartDeck's fixed-height hero/mini slots) -- AddRecordPage's field-set
block is a natural-height vertical form section, not a fixed-size chart container, so the wrapper
needs no explicit sizing classes.

## Current swap structure (read the file fresh before editing -- this is a summary, not a substitute)

Today, inside the `return (...)` of `AddRecordPage`, immediately after the "Record type" button group
and before the Submit button:
```
{recordType === "lab" && (
  <LabFields key={fieldsKey} onDraftChange={setDraftBody} />
)}
{recordType === "incident" && (
  <IncidentFields key={fieldsKey} onDraftChange={setDraftBody} />
)}
{recordType === "procedure" && (
  <ProcedureFields key={fieldsKey} onDraftChange={setDraftBody} />
)}
```
Each of the three field-set components carries the SAME `key={fieldsKey}` prop individually. This
plan removes `key={fieldsKey}` from all three individual elements and instead wraps the whole
three-way conditional in `<div key={fieldsKey}><FadeSwap>...</FadeSwap></div>`. Only one of the three
conditionals is ever truthy at a time, so `FadeSwap` always receives exactly one child element (or
`false`, which React renders as nothing) -- this is the identical children shape ChartDeck's
`FadeSwap` already handles for `entry.mini(data)` and `active.hero(data)`.
