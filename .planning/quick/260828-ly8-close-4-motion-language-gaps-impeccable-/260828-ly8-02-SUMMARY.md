## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 - Bug, discovered during Task 2 live verification] ChartTooltip's Close button was unclickable via real pointer events**
- **Found during:** Task 2, live-DOM verification step 2 (close-then-reopen replay check) — Playwright's real-click actionability check reported the Close button's click was intercepted by an SVG `<path>` (a `ReferenceArea` rect) underneath it
- **Issue:** Recharts' `TooltipBoundingBox` component hardcodes `pointerEvents: 'none'` on the tooltip's ancestor wrapper div (`recharts-tooltip-wrapper`) — a sensible default for hover tooltips (don't steal pointer events from the chart underneath), but it silently makes EVERY element inside a click-persistent tooltip's content non-clickable via real mouse input, including the required ≥48px Close button (D-09's explicit UX requirement). This was invisible in unit tests because `fireEvent.click()` dispatches directly to the target element and does not respect CSS `pointer-events` hit-testing, and it was invisible in manual keyboard-only testing because Escape (a `keydown` listener, unrelated to pointer-events) still worked correctly.
- **Fix:** Added `pointerEvents: "auto"` to the dialog root's own inline `style` object. CSS allows a descendant to explicitly opt back into pointer-event handling even when an ancestor sets `pointer-events: none` — this restores real click handling for the whole dialog subtree without touching Recharts' own `<Tooltip>` usage in `BPTimeline.tsx`/`PulseTrend.tsx` (out of this plan's file scope).
- **Files modified:** `frontend/src/components/charts/ChartTooltip.tsx`
- **Verification:** Live Playwright click on the Close button now succeeds without an actionability-interception error; confirmed via `elementFromPoint` inspection before/after the fix
- **Committed in:** `c940aa6`

**2. [Rule 1 - Bug, discovered during Task 2 live verification] Close button click was immediately undone by the owning chart's click-to-reshow handler**
- **Found during:** Task 2, live-DOM verification step 2, immediately after fixing #1 above — the dialog remained visible after clicking Close
- **Issue:** `BPTimeline.tsx` and `PulseTrend.tsx` both pass `onClick={hero ? () => setDismissed(false) : undefined}` to Recharts' `<LineChart>`, intended to re-show the tooltip when the user clicks a NEW data point after dismissing. Because this `onClick` is attached to the whole chart wrapper (not scoped to clicks on plotted data points), and because fix #1 above made the Close button's click a real, bubbling DOM event, a Close click now bubbled from the button through the Recharts wrapper into that chart-level handler — calling `setDismissed(true)` (from `onClose`) and `setDismissed(false)` (from the chart's own handler) in the same event, with the chart's ancestor handler firing second and winning.
- **Fix:** Added `e.stopPropagation()` to the Close button's `onClick` handler before calling `onClose()`, keeping the click scoped to the button's own dismiss action. Fixed entirely within `ChartTooltip.tsx` — `BPTimeline.tsx`/`PulseTrend.tsx`'s `<LineChart onClick>` (out of this plan's scope) is untouched.
- **Files modified:** `frontend/src/components/charts/ChartTooltip.tsx`
- **Verification:** Live Playwright verification confirmed Close now genuinely dismisses the dialog, and a subsequent click on a different data point correctly reopens it with the entrance transition replaying from `opacity-0`/`motion-safe:scale-95`
- **Committed in:** `c940aa6`

## Issues Encountered
- Live verification's original approach of reading `className` "immediately after `page.mouse.click()`" was unreliable: a real CDP mouse round-trip (down + up + click IPC) reliably takes longer than the ~16-32ms double-rAF window it was racing against, so every attempt already showed the settled `opacity-100` state. Resolved by freezing `window.requestAnimationFrame` in-page before the click and manually batch-draining the queue as two discrete "frames" afterward (batch-draining, not a naive single-callback `shift()`, because React's own scheduler and other page consumers share the same global rAF queue). This is a test-harness technique only — no application code was changed for this.
- Vite's `.env` file precedence initially tripped up isolated-server setup: `.env.local` does NOT override `.env.development` (mode-specific files outrank `.local` files in Vite's precedence order) — had to use `.env.development.local` to point the isolated frontend (port 5182) at the isolated backend (port 8012) instead.
- `backend/.env` and `backend/dev.db` did not exist in this fresh worktree (gitignored, not present at worktree creation) — copied from the main checkout into a scratch location per this plan's own documented recipe, then into the worktree's `backend/` directory (also gitignored, confirmed via `git check-ignore`) to run the isolated backend server; deleted after verification.
- `npx tsc -b` initially failed: the test fixture's `payload` prop was typed as a bare `Reading` object, but `ChartTooltipProps.payload` expects Recharts' actual injected shape (`{ payload?: TimePoint }`, where `TimePoint` wraps `Reading` plus `ts`/`systolic`/`diastolic`/`pulse`). Fixed by building the fixture via the same `toTimePoints()` helper `BPTimeline.tsx`/`PulseTrend.tsx` already use, rather than hand-authoring a `TimePoint` shape.
