## Investigation finding: Recharts' `trigger="click"` mount behavior (already verified at planning time)

Read `node_modules/recharts/es6/component/Tooltip.js` and `TooltipBoundingBox.js` (recharts 3.9.2,
already installed) if you want to re-confirm this yourself. Summary: `<Tooltip content={<ChartTooltip
.../>} trigger="click" />` (used identically in `BPTimeline.tsx` and `PulseTrend.tsx`, both hero-only
via `{hero && <Tooltip .../>}`) calls `React.cloneElement(content, tooltipContentProps)` on every
render of Recharts' internal `Tooltip` component, injecting fresh `active`/`payload`/etc. props into
the SAME `ChartTooltip` element every time (same component instance across many prop updates -- no
remount from Recharts' side, so `ChartTooltip`'s own `useState`/`useEffect` hooks persist correctly
across visibility toggles). Recharts wraps that rendered content in its own `TooltipBoundingBox`,
which ALWAYS stays mounted and only toggles `visibility: hidden`/`visible` via inline style -- but
that wrapper is Recharts-internal, not something this file touches. What actually determines whether
OUR `role="dialog"` div exists in the DOM is `ChartTooltip`'s OWN early return: `const visible =
Boolean(active) && !dismissed && reading !== undefined; ... if (!visible || reading === undefined)
return null;`. Because that early return flips between `null` and a real element tree, React
genuinely removes/inserts that DOM subtree on every visibility change -- functionally a fresh mount
each time, even though the `ChartTooltip` component instance itself persists. This is exactly the
shape `ChartDeck.tsx`'s `FadeSwap` helper is designed for (see that function's own comment: "Double
rAF guarantees the initial styles are painted before the toggle so the transition actually runs") --
reuse that same double-rAF technique here, scaled to this component's own state (`entered`, keyed on
`visible` rather than on a changing `key`).

## Motion-reduce treatment for THIS surface differs from the other three plans in this quick task

Unlike GuideOverlay/DateRangePicker/AddRecordPage (which all use `motion-reduce:transition-none` --
fully instant, no animated transition at all under reduced motion), THIS component's specific
requirement is: opacity keeps animating under reduced motion, only the scale/transform is dropped.
Achieve this with a motion-variant SPLIT on the `transition-property` itself rather than a single
`transition-none` override:
- `motion-safe:transition-[opacity,transform]` -- under standard motion, both opacity and transform
  animate together.
- `motion-reduce:transition-opacity` -- under reduced motion, only opacity animates; transform is
  simply never given a transition (and never given a non-default value either -- see below).
- The `entered ? "opacity-100" : "opacity-0"` classes are UNPREFIXED (always active in both modes) so
  opacity always toggles and therefore always animates via whichever `transition-*` class matched.
- The `entered ? "scale-100" : "scale-95"` classes are prefixed `motion-safe:scale-100` /
  `motion-safe:scale-95` -- under reduced motion neither ever applies, so `transform` stays at its
  browser default (`none`) throughout, meaning there is nothing to animate for the dropped scale
  component (this is what "no scale" means here, as opposed to disabling the transition outright).
- `duration-[150ms] ease-out` apply unprefixed in both modes (a duration on a property that never
  changes, i.e. `transform` under reduced motion, is inert -- harmless).
