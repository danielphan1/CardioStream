<objective>
Build the three form field-sets — Lab, Incident, Procedure — as self-contained components that
own their own local input state, compute their own required-field validity, and report the
current, ready-to-POST request body (or `null` when invalid) up to whichever parent mounts them.

Purpose: isolate all per-resource field knowledge (which fields exist, which are required, the
NaN-guard on optional numeric fields, the date+time combine for Incident) into three small,
independently-readable components, so Plan 08-03's `AddRecordPage` container only needs to know
"mount the active type, read its draft body, enable Submit when non-null" — no per-type logic
lives in the container.
Output: `LabFields.tsx`, `ProcedureFields.tsx`, `IncidentFields.tsx`, each exporting a component
with the shared `{ onDraftChange: (body: XCreate | null) => void }` prop contract, plus a
dedicated Vitest behavior-test file per component proving the required-field gating and the
phase's two correctness-critical guards (Pitfall 3's NaN→null block, Pitfall 4/5's Incident
time/format guards).
</objective>

<interface_contract>
## Field-set prop contract (locked by this plan — Plan 08-03 depends on it exactly)

Each of the three components takes exactly one prop:

```
type LabFieldsProps = { onDraftChange: (body: LabResultCreate | null) => void };
type IncidentFieldsProps = { onDraftChange: (body: IncidentCreate | null) => void };
type ProcedureFieldsProps = { onDraftChange: (body: ProcedureCreate | null) => void };
```

No `value`/initial-state props — each component owns its own `useState` from an empty initial
value. The parent (`AddRecordPage`, Plan 08-03) resets a field-set by changing its React `key`
(forcing an unmount/remount), never by passing new props into a mounted instance. This is why
these components need no imperative reset method and no controlled-from-outside state.

Each component computes, on every render, a `canSubmit: boolean` from its own required-field and
numeric-format rules, and the exact `XCreate` body object it would submit. In a `useEffect` whose
dependency array lists the individual primitive field-state values (never the constructed body
object itself, which is a new reference every render and would loop), call
`onDraftChange(canSubmit ? body : null)`. This fires once on mount (with `null`, since required
fields start empty) and again on every keystroke that changes validity or content.

Each component's optional string fields are trimmed and included as `undefined` (key omitted from
the body) when empty, exactly as the `?:` markers on `LabResultCreate`/`IncidentCreate`/
`ProcedureCreate` (Plan 08-01) express — never send an empty string for an unfilled optional
field.
</interface_contract>

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-08-01 | Tampering (data integrity) | `LabFields.tsx`'s `result`/`range_low`/`range_high` numeric fields | mitigate | Explicit `Number.isFinite(Number(text))` gate before including any optional numeric field in the emitted body — `JSON.stringify({ result: NaN })` silently becomes `{"result":null}`, and the backend's `Optional[float]` accepts that with no 422, so the client must not let a caregiver's typo become an ambiguous `null` (RESEARCH Pitfall 3). Test-enforced: `LabFields.test.tsx` asserts `onDraftChange` is called with strictly `null` when `Result` contains non-numeric text. |
| T-08-02 | Tampering (client-side validation bypass) | Required-field gating (`canSubmit`) in all three field-sets | accept | Not a security boundary — Pydantic independently 422s a malformed/incomplete body server-side (Phase 7 T-07-02, closed) regardless of what `canSubmit` allowed the caregiver to attempt. These components are a UX nicety only. |
| T-08-03 | Tampering (XSS) | Free-text values (`test_name`, `incident_type`, `duration`, `notes`, etc.) held in these components' local state | accept | These components never render caregiver-typed text back as HTML (no `dangerouslySetInnerHTML`); values are only held in controlled-input `value` props and later rendered as plain confirmation text by `AddRecordPage` (Plan 08-03), where React's JSX auto-escaping applies (same T-02-08 precedent as `ReadingsTable`'s `notes` column). |

No new trust boundary is introduced by this plan — these are pure client-side form-state
components with no network calls of their own.
</threat_model>
