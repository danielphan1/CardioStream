# Phase 10 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

This phase adds exactly one new visible control (a header mute/quiet toggle,
TTS-02) and one new transient state to an existing surface (`CommandBar`'s
"Speaking…" indicator, D-05) — it introduces **zero new color tokens** and
**zero new typography roles**. Every other requirement (TTS-01, TTS-03,
TTS-04, TTS-05) is audio/behavioral, not visual: the spoken text is the
existing `composeConfirmation()` output already rendered on screen, and the
existing `aria-live="polite"` confirmation region is explicitly locked
(D-04) to keep firing unconditionally, mute or not. Same reasoning as
Phases 6/8/9: this is a continuation phase on an already-shipped,
comprehensively documented, hand-rolled Tailwind v4 system
(`frontend/src/index.css`, header comment: "Design-token system —
02-UI-SPEC.md locked palette"). No `components.json` exists and none is
introduced — a shadcn gate would fork the visual language mid-project for
one toggle button and one status line. Registry safety: not applicable.

`10-CONTEXT.md` already locked D-01 through D-06 (schema shape, header
placement, persistence pattern, aria-live coexistence, "Speaking…" state,
barge-in scope) and left a short, explicitly cosmetic "Claude's Discretion"
list (exact toggle label/icon, spoken-text source, mic-pause-state naming
and copy). This document resolves every item on that list so the executor
has zero visual ambiguity left to invent.

## Spacing Scale

Declared values (multiples of 4), as already used throughout the codebase — no new scale introduced:

| Token | Value | Usage in this phase |
|-------|-------|-------|
| xs | 4px | Icon-to-glyph gap is not used standalone this phase (icons sit inside `gap-2` groups below) |
| sm | 8px | `gap-2` inside the toggle button (icon-to-label) and inside the "Speaking…" indicator (icon-to-word) — matches every existing `Header.tsx` button and `CommandBar.tsx`'s Working indicator exactly |
| md | 16px | `gap-4` between header-right controls (Theme toggle, new Voice Replies toggle, Upload/Add Record, Log out) — existing `Header.tsx` row gap, unchanged |
| lg | 24px | Not introduced this phase |
| xl | 32px | Not introduced this phase |
| 2xl | 48px | Minimum interactive target height (`min-h-12`) on the new toggle button — non-negotiable, matches every other header control |
| 3xl | 64px | Not introduced this phase |

Exceptions: `mt-3` (12px) on the new "Speaking…" indicator — not one of the
seven named tokens above, but still multiple-of-4 compliant, and required
to exactly match `CommandBar.tsx`'s existing pre-Phase-10 vertical rhythm
(`Working…` indicator and the `aria-live` confirmation paragraph both
already use `mt-3`). This is an inherited precedent, not a new deviation.

## Typography

Full system (existing, reused — no new type role introduced).

| Role | Size | Weight | Line Height | Used for in this phase |
|------|------|--------|-------------|------------------------|
| Body | 18px | 400 (regular) | 1.5 | Not used directly this phase (see hybrid note below) |
| Label | 20px | 700 (bold) | 1.2 | New toggle button text ("Voice Replies: On" / "Voice Replies: Off") — matches `Header.tsx`'s existing `text-[20px] font-bold` button treatment exactly |
| Heading (h2) | 24px | 700 (bold) | 1.2 | Not used this phase |
| Display | 32px | 700 (bold) | 1.2 | Not used this phase |

**Inherited hybrid exception (pre-existing, not introduced by this
phase):** `CommandBar.tsx`'s "Working…" indicator uses `text-[18px]
font-bold` — 18px size (Body) at 700 weight (Label), a hybrid that predates
Phase 10. The new "Speaking…" indicator (D-05) must use this **exact same**
hybrid (`text-[18px] font-bold text-[var(--color-ink)]`) so the two
transient status lines read as one consistent visual family, not two
different styles. Do not "fix" this to pure Body or pure Label — matching
the existing indicator takes precedence over strict role purity here.

## Color

| Role | Value (light / dark) | Usage |
|------|------|-------|
| Dominant (60%) | `--color-foam` (`#F2F7F5` / `#0B1626`) | Page/header background (unchanged) |
| Secondary (30%) | `--color-sky` (`#E2EDF2` / `#13233A`) | New toggle button's background surface, both On and Off states — matches every other header control |
| Accent (10%) | `--color-accent` (`#14213D` / `#8FC1D4`) | **No new use this phase.** The toggle is explicitly NOT accent-filled (D-02: "inactive-control styling, bordered, not accent-fill") — same treatment as the Theme toggle, Upload/Add Record, and Log out buttons |
| Destructive | none — this project has no separate destructive/danger color | Not applicable; this phase has no destructive action |

**Accent reserved-for list is unchanged by this phase** (still: Send
button, active/pressed date/AM-PM/category filter chips, active overlay
toggle fills, CommandBar's listening ring, Log-out confirm button, Phase
8's active type-switcher segment/enabled Submit button). The new Voice
Replies toggle is deliberately excluded from this list, in both On and Off
states — it is styled identically to the Theme toggle it sits beside.

**Zero new color tokens this phase.** Both the toggle button and the
"Speaking…" indicator use only `--color-ink` (text/icon/border) and
`--color-sky` (button surface) — colors that already exist. State
(replies-on vs. replies-off; speaking vs. not-speaking) is communicated
entirely through **icon + word**, never through color, matching the
project's non-color-only convention with zero exceptions.

**Explicit prohibition:** do not introduce a new color to distinguish the
toggle's On/Off states (e.g., a green "on" tint) — the Theme toggle proves
the established pattern (icon + word swap only, same ink/sky palette in
both states), and Phase 6's/9's "never conflate state with an unreviewed
new color" precedent applies here too.

## Copywriting Contract

| Element | Copy |
|---------|------|
| Primary CTA | Not a data-entry CTA — this phase's one new interactive control is the mute/quiet toggle button. On state: **"Voice Replies: On"** (icon `Volume2`). Off state: **"Voice Replies: Off"** (icon `VolumeX`). Resolves the "exact mute-toggle label/icon" Claude's Discretion item — named "Voice Replies" (not "Mute"/"Unmute" or bare "Voice") specifically to avoid collision with the pre-existing mic button's "Start/Stop voice control" — this toggle controls spoken *output*, the mic controls voice *input*, and the label must never be confusable with it |
| Empty state | Not applicable — this phase adds no data list or empty collection |
| Error state | **Not applicable by design — no error copy is ever shown for a TTS failure.** If `speechSynthesis` is unsupported, blocked, or an utterance fails to play, the dashboard degrades silently to visual-only: the pre-existing `aria-live` confirmation text (D-04, never suppressed) already carries the full meaning. Surfacing a "voice reply failed" banner would violate the "never alarming, nothing is actually broken" precedent (Phase 6) for a convenience layer whose failure mode is silence, not data loss |
| Destructive confirmation | Not applicable — toggling spoken replies off is instantaneous, reversible, and non-destructive (no confirm dialog), exactly like the Theme toggle it's styled after |
| "Speaking…" indicator (D-05, new) | **"Speaking…"** (word, sentence-case — not `"SPEAKING…"` — see rationale below) + `Volume2` icon (`aria-hidden`), shown only while an utterance is actively playing |

**Why "Speaking…" is single-cased, unlike "Working…"/"WORKING…":**
`CommandBar.tsx`'s existing Working indicator deliberately cases itself
differently per trigger path (`"Working…"` for typed/manual submits,
`"WORKING…"` for voice-triggered ones) because that distinction is about
*which input path* is waiting on the agent. "Speaking…" describes a single
shared audio state that is reached identically whether the just-applied
command came from the text box or the mic (Code Context: "a TTS trigger
needs to be wired into BOTH [`CommandBar.onApplied` and
`useVoiceCommand.handleSuccess`], not just one") — there is no
input-path distinction left to encode by the time speech starts, so one
casing is correct and simpler.

**Mic-pause-for-speech state gets NO new visible copy.** TTS-04's
mic-pauses-while-speaking behavior must **not** reuse the existing
`PAUSED_COPY` string (`"Voice is paused — tap the mic to start listening
again."` / `VOICE_PAUSED_COPY` `"Voice paused — tap to resume"`) — that
copy is reserved for D-14's fatal-error state and explicitly tells the user
an action (tap) is required, which would be **false** for a TTS-driven
pause that auto-resumes with no user action. The "Speaking…" indicator
(above) is the entire explanation a sighted user needs for why the mic
went quiet (D-05's own stated rationale); no additional line of copy is
introduced for this sub-state. Whatever new `VoiceState` value research/
planning assigns to it (CONTEXT.md: `"paused"` is taken) must render with
**no** message text in `CommandBar`'s `lineText` — leave that slot blank
while `isSpeaking` is true, letting the "Speaking…" indicator be the sole
visible signal.

**Icon prohibition:** the mic button itself (`Mic`/`MicOff` swap) must
**not** switch to `MicOff` during the TTS-driven pause. That visual swap is
reserved for D-14's fatal `"paused"` state (mic genuinely dead until a
tap). Swapping it during a benign, auto-resuming, sub-second TTS pause
would visually lie about the mic's actual (recoverable, unattended)
condition. The mic button stays in its normal `Mic` icon during
speech-triggered pause; only the new "Speaking…" indicator communicates
the pause.

## Phase-Specific Component Contract

*(Additional detail beyond the standard template — the executor's primary visual reference.)*

### `Header.tsx` — new Voice Replies toggle (D-02, TTS-02)

New button, placed **immediately after the Theme toggle and before
Upload/Add Record/Log out** in the header-right flex row — grouping the two
"site-wide display/output preference" toggles (Theme, Voice Replies)
together, ahead of the navigation/session controls. Follows the Theme
toggle's markup contract exactly (icon + text, never icon-only,
`aria-pressed`, ≥48px target, bordered `--color-sky` surface, never
accent-filled):

```tsx
import { Volume2, VolumeX } from "lucide-react";
import { useSpeech } from "../store/speech";

// ...inside Header, in the header-right controls row, right after the
// existing Theme toggle button:
const speechEnabled = useSpeech((s) => s.enabled);
const toggleSpeech = useSpeech((s) => s.toggle);

<button
  type="button"
  onClick={toggleSpeech}
  aria-pressed={speechEnabled}
  className="flex min-h-12 items-center gap-2 rounded-lg border-2 border-[var(--color-ink)] bg-[var(--color-sky)] px-4 text-[20px] font-bold text-[var(--color-ink)]"
>
  {speechEnabled ? (
    <Volume2 aria-hidden="true" size={24} />
  ) : (
    <VolumeX aria-hidden="true" size={24} />
  )}
  {speechEnabled ? "Voice Replies: On" : "Voice Replies: Off"}
</button>
```

No separate `aria-label` — the visible text is the accessible name
(matches the Theme toggle's own convention, which has no `aria-label`
either). `size={24}` matches the Theme toggle's icon size exactly (not the
smaller `size={20}` used by Phase 9's inline overlay chips — this is a
header-zone control, not a chip).

**Store:** `frontend/src/store/speech.ts`, a new zustand store templated
directly on `store/theme.ts` (D-03) — persisted boolean, `localStorage` key
(e.g. `"hv-speech"`), guarded try/catch on both read and write so a
blocked/unavailable localStorage degrades to session-only (default `true`,
i.e., on) rather than breaking bootstrap. Default state is **on** per
TTS-02.

### `CommandBar.tsx` — new "Speaking…" indicator (D-05)

Renders as a **third**, independent conditional block — NOT a replacement
for the existing Working indicator or the `aria-live` confirmation
paragraph, both of which are unchanged and keep rendering under their
existing conditions (D-04: the confirmation must never be suppressed).
Render order in the JSX (top to bottom, unchanged positions for the first
and third blocks):

```tsx
{/* 1. existing — unchanged */}
{anyWorking && (
  <p className="mt-3 flex items-center gap-2 text-[18px] font-bold text-[var(--color-ink)]">
    {/* spinner + Working…/WORKING… — unchanged */}
  </p>
)}

{/* 2. NEW — Speaking… indicator (D-05). Plain paragraph, no aria-live:
    the meaning is already announced by the confirmation region below (and,
    when unmuted, by the audio itself) — a second live announcement here
    would double-speak the same event for screen-reader users. */}
{isSpeaking && (
  <p className="mt-3 flex items-center gap-2 text-[18px] font-bold text-[var(--color-ink)]">
    <Volume2
      aria-hidden="true"
      className="h-5 w-5 motion-safe:animate-pulse motion-reduce:animate-none"
    />
    Speaking…
  </p>
)}

{/* 3. existing — unchanged, still fires regardless of mute state (D-04) */}
{!anyWorking && lineText !== "" && (
  <p aria-live="polite" className="mt-3 flex items-start gap-2 text-[18px] ...">
    {/* confirmation text — unchanged */}
  </p>
)}
```

`isSpeaking` must be read from wherever the shared speech controller lives
(a new store/hook analogous to `useAgentStatus`'s existing cross-component
zustand pattern), **not** local `useState` scoped to one call site — the
trigger may originate from either `CommandBar.onApplied` (text path) or
`useVoiceCommand.handleSuccess` (voice path), and both must produce the
same visible "Speaking…" state in `CommandBar` regardless of which one
fired (Code Context: "two call sites... not shared code" for the trigger
itself, but the resulting visible state must still be one shared signal).
Exact hook/store shape is research/planning's call (10-CONTEXT.md, Claude's
Discretion) — this contract only fixes what it must render and where.

`motion-safe:animate-pulse` / `motion-reduce:animate-none` on the icon
mirrors `CommandBar.tsx`'s existing spinner reduced-motion handling
(D-09 precedent) — a gentle pulse, not a spin (spinning is reserved for
"waiting on a response"; speaking is an active, not a waiting, state).

### Voice command vocabulary (D-01 — schema shape locked, phrasing is Claude's job)

Per D-01, the new agent action mirrors `ToggleDataset` exactly (single
concept, explicit on/off, never a flip). Naming consistency note (not a
schema spec — that's research/planning's file to write): use **"Voice
Replies"** as the one, single term for this concept everywhere it appears
in UI copy, the system prompt, and (later) the Phase 11 guide's "what can I
say" reference — never interchange it with "mute," "sound," or "audio" in
different places, so the voice-command vocabulary the guide documents
matches the button label verbatim.

| Say (example — Claude owns exact phrasing/synonyms) | State |
|-----|-------|
| "turn off voice replies" / "mute the voice replies" / "stop talking" | `off` |
| "turn on voice replies" / "unmute" / "start talking" | `on` |
