<objective>
Wire the text-input path of the command bar to the speech store built in Plan 10-02: call
`speak(msg)` with the exact full on-screen confirmation string on an applied reply (TTS-01, only
from `onApplied` — never from `clarify`/`refuse`/`unclear`/`unavailable`), prime
`speechSynthesis` inside the two real user-gesture handlers (`onSubmit`, `onMicClick`) so iOS
Safari's/Chrome's gesture-unlock requirement is satisfied for both text-only and voice-first
users (TTS-05, Pitfall 1), extend `sessionOpen` so a mic tap during a TTS-driven pause closes the
whole session correctly, and add the new "Speaking…" indicator block (D-05) locked by
10-UI-SPEC.md.

Purpose: TTS-01 requires the SAME confirmation text already shown visually to be spoken aloud on
applied commands only. D-04 requires the existing `aria-live` confirmation to keep firing
unconditionally regardless of mute state — this plan changes nothing about that region's own
gating, only adds a sibling block.
Output: Submitting a text command that gets applied now speaks the exact echoed confirmation
aloud (when unmuted), shows a "Speaking…" indicator while it plays, and primes iOS/Chrome's
gesture-unlock on every real user tap.
</objective>
