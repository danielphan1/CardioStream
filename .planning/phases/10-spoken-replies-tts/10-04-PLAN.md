<objective>
Wire the voice path's mic pause/resume around TTS playback (TTS-04) and the voice-path's
`speak()` trigger (TTS-01) into `useVoiceCommand.ts`: add a new `"speaking"` `VoiceState` value
(a peer of the existing `"paused"` D-14 fatal state — never reused, per 10-CONTEXT.md), a
`speakingRef` mirroring the file's existing ref-based construct-once-handler convention, an
`armedRef`-gated effect that aborts the recognizer when `isSpeaking` flips true and restarts it
when it flips false (without ever touching `armedRef`, preserving D-13's explicit-stop-only
invariant), a guard inside the existing `onend` handler so the TTS-driven `abort()` never races
the invisible restart loop (Pitfall 4), and an extension to the existing `onVisibility` handler
so backgrounding mid-utterance proactively cancels speech rather than trusting `onend`/`onerror`
to ever fire on a backgrounded iOS Safari tab (Pitfall 6).

Purpose: TTS-04 requires the mic to pause while the dashboard speaks and resume right after, so
it never mishears its own confirmation as a new command — but ONLY when a voice session is
genuinely open; a text-only caregiver's typed command must never silently activate their
microphone (the load-bearing `armedRef` gate). handleSuccess's applied-case speak() call is one of exactly two code paths (the other is Plan 10-03's CommandBar.onApplied) that may ever trigger speech (D-06) — nothing in this file's filter-store interactions becomes a new speech trigger source.
Output: An armed mic pauses during TTS playback and resumes automatically after; a never-armed
mic is completely unaffected by any TTS event; backgrounding mid-utterance can't leave the
recognizer stuck.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|--------------|
| `isSpeaking` global signal → recognizer lifecycle | A store-level boolean, written from either input path, now controls WHEN the microphone is actively listening — an incorrect gate here would either silently activate a text-only user's mic (Pitfall 3) or leave the mic permanently paused (Pitfall 4/6) |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-10-08 | Denial of Service (UX) — mic self-mishearing feedback loop | The new isSpeaking pause/resume effect | mitigate | The effect aborts the recognizer BEFORE the browser starts emitting the TTS audio's own transcript back into `onresult`, and the `armedRef` gate ensures this mechanic only ever engages when a voice session was already genuinely open — matches TTS-04's exact scope. |
| T-10-09 | Denial of Service (UX) — mic silently activated for a user who never opted in | The isSpeaking effect firing for a text-only submit | mitigate | Explicit `if (!armedRef.current) return;` early exit (Pitfall 3) — the effect is fully inert for any user who has not tapped the mic button, verified by a dedicated regression test in Task 2. |
| T-10-10 | Repudiation / stuck state | iOS backgrounding leaving the recognizer or `isSpeaking` permanently stuck | mitigate | `cancelForBackground()` (Plan 10-02) is called proactively on the `hidden` transition rather than waiting on `onend`/`onerror`, which may never fire on a backgrounded iOS Safari tab (Pitfall 6, documented platform bug). |

No new backend surface, no new dependency, no change to the existing D-13 explicit-stop-only
invariant (verified structurally — this task never assigns to `armedRef`).
