  <what-built>
The full spoken-replies feature: after an applied voice/agent command, the dashboard now speaks
the same confirmation text already shown on screen (TTS-01); a persisted, voice-reachable header
toggle mutes/unmutes spoken replies, on by default (TTS-02); only one utterance ever plays at a
time via a cancel-and-replace guard (TTS-03); the mic pauses while the dashboard is speaking and
resumes right after (TTS-04); and gesture-unlock priming + proactive backgrounding-cancel handle

  </what-built>
  <how-to-verify>
1. Run `cd backend && python -m pytest` and `cd frontend && npm test -- --run` — confirm both
   suites are fully green (0 failures) before real-device testing.
2. Start both dev servers (`cd backend && uvicorn app.main:app --reload`, `cd frontend && npm
   run dev`), log in, and open the dashboard on Chrome or Edge desktop.
3. Confirm the header shows a "Voice Replies: On" button (Volume2 icon) immediately after the
   Theme toggle, `aria-pressed="true"` (inspect via devtools).
4. Type a command into the command bar that will resolve to "unclear" or "unavailable" (e.g. the
   agent has no API credits in this environment, so any text submit will surface a canned reply)
   and confirm the confirmation text renders in the bar as usual — this environment's
   billing-gated agent means TTS itself cannot be exercised through a live Claude round-trip
   here; instead, temporarily use the browser devtools console to call
   `window.__testSpeak?.()` if a dev-only hook exists, OR (preferred) manually invoke
   `import('/src/store/speech.ts').then(m => m.useSpeech.getState().speak("Showing blood
   pressure, last 30 days"))` in the console to exercise the real `speechSynthesis` pathway
   end-to-end while the backend billing gap is outstanding (tracked separately, not a Phase 10
   blocker per PROJECT.md/STATE.md).
5. Confirm the confirmation is audibly spoken aloud, and a "Speaking…" indicator (Volume2 icon,
   pulsing) appears in the command bar while it plays, then disappears when speech ends.
6. Click the "Voice Replies: On" button to mute — confirm it now reads "Voice Replies: Off"
   (VolumeX icon), and repeating step 4's console call produces NO audible speech (the aria-live
   confirmation text, if applicable, still renders — D-04). Reload the page and confirm the
   button still reads "Voice Replies: Off" (persistence, D-03). Click it again to re-enable
   before continuing.
7. Tap the mic button to start a voice session (Chrome/Edge honor real speech recognition here).
   Say "dashboard show my pulse" (or use the console call from step 4 to simulate a spoken
   reply while the mic is armed) and confirm: the mic visibly pauses (no red "listening" ring,
   command bar shows "Speaking…") while the reply plays, then automatically resumes listening
   (green ring returns) right after — without you tapping the mic again.
8. Trigger two spoken replies in quick succession (e.g. two console `speak()` calls back to
   back) — confirm only the SECOND reply is heard, cleanly, with no audio overlap or garble
   (TTS-03).
9. Switch to Safari desktop and repeat steps 3-8.
10. On a real iOS Safari device (the highest-risk platform per RESEARCH Assumptions A5/A6):
    open the dashboard, tap the mic button ONCE (or submit one typed command), then trigger a
    SECOND spoken reply via the console (or a second voice command) WITHOUT any further tap —
    confirm it still speaks (proves the gesture-unlock primed on the first tap persists for the
    rest of the page session).
11. On the same iOS device, start a spoken reply, then background the app (switch to another app
    or the home screen) mid-utterance, then return to the dashboard — confirm the app has not
    become permanently stuck (trigger one more spoken reply and confirm it still plays; the
    "Speaking…" indicator should not be stuck on indefinitely).
12. On the iOS device, confirm the mic pause/resume from step 7 also works correctly (no
    self-mishearing, resumes automatically).
