<objective>
Build the filter layer's pure and presentational pieces before the popover consumes them (UI-SPEC §5.3/§5.4) and re-treat the category chips per §4.4: extract the live filter sentence into a pure function, add `activeFilterCount`, retreat the selected chip from a solid clinical fill plus ink ring to a 12% tint of its own hue with a hue-matched border, and create the single-live-region `FilterStateBlock`.

Purpose: §5.4 is a hard requirement, not a preference — the primary user cannot reliably open a popover and cannot see one he has not opened, so the applied state must stay visible and announced on the page at all times. Consolidating three separate `aria-live` attributes into one region is what stops a single agent command from firing four or five racing polite utterances on top of the Command Bar's own region and the spoken confirmation. Nothing is mounted or relocated here — plan 16.1-07 does that — so this commit is behaviour-neutral and `FilterBar.test.tsx` stays green through it.

Output: `buildFilterSentence` and `activeFilterCount` in `lib/showSentence.ts` with unit tests; the four `DEFAULT_*` maps exported from the store; chips re-treated per §4.4; `FilterStateBlock` created and tested but not yet mounted.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| agent-applied filter delta → announced state | `applyAgentFilters` mutates the store from outside the React tree; this block is what renders and announces the result. Consolidating to one polite region is an integrity property of that boundary: a deterministic single announcement instead of a race between three. |
| already-authenticated store state → derived count | `activeFilterCount` reads only in-memory store state that has already crossed the Phase 5 auth gate. It performs no I/O and reaches no backend. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-16.1-13 | Tampering | `buildFilterSentence` extraction | mitigate | The extraction is behaviour-neutral and gated by `FilterBar.test.tsx` passing against an unmodified test file, so a reworded or reordered string fails the gate rather than silently changing what the user is told is applied |
| T-16.1-14 | Information Disclosure | the always-visible state block | accept | It restates filter state the user chose for their own health data on a password-gated, analytics-free site; no new data leaves the client |
| T-16.1-15 | Denial of Service | multiple `aria-live` regions announcing at once | mitigate | §5.4's single-region consolidation plus the grep gate asserting exactly one `aria-live` attribute in the file prevents the screen-reader flooding that three co-located polite regions would cause |
| T-16.1-16 | Tampering | `activeFilterCount` default comparison | mitigate | Compares against the store's own exported `DEFAULT_*` maps rather than re-typed literals, so a future default change cannot desynchronise the badge from reality |
| T-16.1-17 | Tampering | npm/pip/cargo installs | mitigate | Not applicable: no dependency is added (UI-SPEC §10) — no package-legitimacy checkpoint required |
</threat_model>
