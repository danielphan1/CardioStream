## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| keyboard/switch-access input → overlay focus management | The nav panel decides what is focusable while it covers the content. Getting this wrong strands the primary user away from the mic, so "no trap" and "Close is an explicit ≥48px target" are safety properties of this boundary (D-03/D-04). |
| `/health` response → demo badge rendering | `demoMode` from the already-authenticated `/health` payload decides whether the synthetic-data provenance badge renders. Suppressing it would misrepresent fabricated data as real. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-16.1-18 | Spoofing | the Guest-Demo provenance badge | mitigate | §5.2 puts the badge in the always-visible slim bar rather than behind the menu disclosure, and the acceptance criteria grep-assert it is present in `SlimTopBar.tsx` and absent from `NavPanel.tsx`, so synthetic figures can never be presented as real |
| T-16.1-19 | Denial of Service | nav panel focus handling | mitigate | No focus trap and no Tab handler (grep-gated); the Close control is an explicit ≥48px target and Escape also dismisses, so a voice or switch user always has a route out |
| T-16.1-20 | Information Disclosure | content bleeding through the panel backdrop | mitigate | The separate always-`fixed inset-0` opaque backdrop at `z-40` is inherited from GuideOverlay specifically because it fixes a documented bleed-through regression; a panel relying on its own measured-`top` box would re-open it on a new surface |
| T-16.1-21 | Elevation of Privilege | write destinations in the rail/panel | accept | `ShellNav` reproduces today's `demoMode` suppression of Upload and Add Record exactly; the authoritative gate remains the backend's guest-demo write rejection, untouched here |
