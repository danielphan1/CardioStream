<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| filter store → two views rendering the same filtered data | The Readings view and the Dashboard read one store and one query cache. If the Readings view did not surface the filter controls, a user could land on a table silently narrowed by a filter set elsewhere and read it as the complete record — a clinical misreading of their own data. |
| view state → which surfaces mount | Routing is a zustand state flip, not a URL. No new navigation surface and no new data path is introduced; `ReadingsView` mounts the same already-authenticated read hooks the Dashboard mounts. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-16.1-39 | Spoofing | a filtered table read as the complete record | mitigate | §5.8 puts the filter trigger row and the always-visible live state block on the Readings view, and the smoke test asserts both render there, so the applied narrowing is always stated on the surface that shows the rows |
| T-16.1-40 | Information Disclosure | a new view mounting data hooks | accept | `ReadingsView` is rendered only from inside the authenticated tree, below the same Phase 5 auth gate as the Dashboard, and calls the identical already-shipped read hooks — no new endpoint and no new fetch before authentication |
| T-16.1-41 | Repudiation | duplicate announcements across two views | mitigate | Both views get the state block from the single `AppShell` `showFilters` cluster rather than rendering their own, so there is still exactly one polite region in the DOM — the criterion `FilterStateBlock.test.tsx` asserts |
| T-16.1-42 | Tampering | npm/pip/cargo installs | mitigate | Not applicable: no dependency is added (UI-SPEC §10) — no package-legitimacy checkpoint required |
</threat_model>
