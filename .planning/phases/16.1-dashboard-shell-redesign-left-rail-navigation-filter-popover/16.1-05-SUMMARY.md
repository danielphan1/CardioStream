## Accomplishments

- **`LeftRail`** — 240px, `shrink-0`, `sticky top-0 h-screen`, `overflow-y-auto`, flat mist fill, 2px depth border on the right edge only. No elevation class and no stacking offset, both load-bearing: UI-SPEC §5.0 depends on the rail staying on the automatic layer so the guide's backdrop covers it completely. The root takes and applies `inert`, which is the reassignment of the attribute that today sits on `App.tsx`'s header wrapper — plan 16.1-06 can hand it straight over.
- **`SlimTopBar`** — flat mist bar, 2px depth bottom border, `min-h-16` as a floor plus `flex-wrap`, so at 375px it wraps to a second row instead of truncating or scrolling sideways. Mark, one `text-label` `<h1>`, the Guest-Demo badge **in the bar**, then a right-pushed utility group holding the icon-plus-text menu trigger (stable id, expanded state, `aria-controls="nav-panel"`) and the always-visible Guide toggle (`id="guide-toggle-button"`, pressed state, never accent-filled).
- **`NavPanel`** — full-width overlay at GuideOverlay's exact geometry with a separate always-`fixed inset-0` opaque mist backdrop, a sticky "Close" bar that receives focus on open, an `<h2>` "Menu" that names the region via `aria-labelledby`, and `<ShellNav onNavigate={onClose} includeGuide={false} />`. `role="group"`, no modal role, no modal attribute, no focus trap, no key handling that cycles focus — all dismissal and focus mechanics come from `useDismissable`.
- **The Guide relocation is the phase's one real defect fix**, and both halves of it are now covered by unit tests rather than browser checks: `SlimTopBar.test.tsx` asserts exactly one `#guide-toggle-button` with its pressed state and both toggle directions, and `NavPanel.test.tsx` asserts zero of them alongside Theme / Voice Replies / Log out still present.

## Decisions Made

- **Hoisted the shared header-chrome class string into one `HEADER_CHROME` constant in `SlimTopBar`.** The plan explicitly anticipated this ("an executor may legitimately hoist it into a single constant") and it is why the `min-h-12` acceptance criterion is a `>= 1` count with the real check pushed into the unit tests — both buttons are asserted to carry it individually.
- **`NavPanel`'s Close button carries no elevation class.** `GuideOverlay`'s equivalent has `shadow-[var(--shadow-elevation)]`, but the plan's explicit class list for this button omits it and the Flat-Sea Rule points the same way. Flagged here because it is the one place these two surfaces are not byte-identical.
- **Added a padding wrapper (`px-4 pb-6 md:px-8`) around `NavPanel`'s `<h2>` and `ShellNav`.** The plan specified the panel's contents and order but no body gutters; this matches `GuideOverlay`'s own `px-4 md:px-8` inner sections and changes nothing about DOM order.
- **Introduced a `HealthProbe` test helper** rather than relying on `findByText(title)` to prove the query had settled. Wave 2's trap note is about absence assertions running against the loading state; for the badge the failure mode is the quieter one (the badge is absent *while loading too*, so `demo: false` would pass vacuously). The probe renders a marker only once the shared `["health"]` cache entry has data, which makes those assertions real.

## Issues Encountered

1. **Expected base drift (#2015), as forewarned.** `git merge-base HEAD 4f8e8a4` returned `e3f6b05`, not the expected base. Resolved with the single `git reset --hard 4f8e8a4…` the worktree check authorises, after confirming a clean working tree. HEAD verified equal to the expected base before any work began.
2. **Three acceptance-grep collisions caused by my own comment prose, caught by running the greps rather than assuming.** Each criterion counts a literal, so naming the token in a comment breaks its own gate:
   - `LeftRail.tsx`: a comment reading "NOT text-heading" made `grep -c "text-heading"` return 1 instead of 0 → reworded to "not the larger display token".
   - `SlimTopBar.tsx`: a comment reading "ms-auto sits on the GROUP" made `grep -c "ms-auto"` return 2 instead of 1 → reworded to "the auto start-margin that pushes it".
   - `NavPanel.tsx`: the trailing not-in-this-panel comment contained `<h1>`, making `grep -c "<h1"` return 1 instead of 0 → reworded to "the page-title heading".

   The same discipline is why `NavPanel.tsx` says "the Guide button's fixed id" rather than quoting it (that count must be 0), avoids the word *stable* entirely (it contains "tab", which the no-focus-trap gate counts), and describes the layer stack in prose rather than quoting `z-40` / `z-50`.
3. **The delayed-unmount test failed on first run.** `vi.advanceTimersByTime` outside `act()` fires the hook's timeout but never flushes React's re-render, so the panel was still in the DOM at 250ms. Wrapped both advances in `act()`, matching `useDismissable.test.ts`'s own precedent, and stubbed `getHealth` with a never-settling promise in that one test so no async state update needs flushing alongside fake timers.
4. **The matchMedia trap was sidestepped rather than worked around.** `LeftRail` does not call `useMediaQuery` itself — plan 16.1-06's shell does the choosing — so rendering the component directly in its test needs no `matchMedia` stub and is not vacuous. The trap's real consequence here is the *opposite* and favourable one: because jsdom renders the slim-bar branch, the relocated Guide control is unit-testable at all, which is exactly what UI-SPEC §5.2's superseding note predicted.
