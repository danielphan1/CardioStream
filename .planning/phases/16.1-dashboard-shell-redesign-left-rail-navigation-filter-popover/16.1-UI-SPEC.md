# Phase 16.1 — UI Design Contract

> Visual and interaction contract for the dashboard shell redesign. Generated by gsd-ui-researcher, verified by gsd-ui-checker.
>
> **Source of truth precedence:** `frontend/src/index.css` (real token values) > this file > `DESIGN.md` (partly stale, see `16.1-CONTEXT.md`). Every RULE named in DESIGN.md (Two-Weight, Dashed-Border, Flat-Sea, No-Off-Screen, Single-Source, One-Signal, Data-Is-Locked) remains authoritative and is honoured below.

## Design System

| Property | Value |
|----------|-------|
| Tool | none (hand-authored token system) |
| Preset | not applicable |
| Component library | none — plain React 19 + Tailwind v4 CSS-first (`@tailwindcss/vite`), no Radix, no Base UI |

## Spacing Scale

Declared values (multiples of 4 — unchanged from the project's working vocabulary):

| xl | 32px | cluster gap inside the content column |

| 3xl | 64px | slim top bar height (<1024px), page gutters at ≥1280px |

Fixed non-scale dimensions (each is a layout constant, not a new spacing token):

| Constant | Value | Why this number |
|---|---|---|
| Rail width | **240px** | locked in CONTEXT. 240 − 2×16 gutter = 208px item width; "Voice Replies: Off" at 20px/700 ≈ 196px + 24px icon + 8px gap wraps to 2 lines, which is allowed (items are `min-h-12`, not fixed-height). |
| Rail breakpoint | **1024px** (`lg:`) | locked in CONTEXT. |
| Slim top bar | **64px** (<1024px) | 48px menu button + 8px padding top and bottom. |
| Vitals row height | **90px** (desktop/tablet) | 12px pad + 25px label line (20px × 1.25) + 41px value line (36px × 1.15) + 12px pad. Tokens used are on-scale (`py-3`); 90px is the computed result, not a declared token. |
| Popover width | **560px** (≥768px) | the widest chip ("Hypertensive Crisis", 20px/700 + 26px checkbox + 12px dot + 16px×2 padding) measures ≈275px, so 560 − 2×24 padding = 512px fits exactly two per row with 8px gap. |

| Category dot | **12px** | reuses StatsStrip's existing legend-dot size. |

Exceptions: the five constants above. No other off-scale value is permitted.

### 4.3 Resolution of the three must-resolve items

#### (1) `--line-diastolic` — derived, not picked

**New values: `#AC40BF` (light) / `#B055BE` (dark).** A deep violet.

*Derivation.* The hue wheel is almost full. Occupied light-theme hues: 3.1 (crisis), 4.4 (hazard), 7.5 (stage 2), 18.7 (pulse), 23.9 (stage 1), 33.3 (brass→focus), 47.5 (elevated), 74.8 (procedures), 156.5 (normal), 168.6 (**the new accent**), 204.0 (hypotension / bradycardia ref), 214.2 (systolic), 216.0 (ink), 263.6 (labs), 325.1 (incidents). That leaves exactly two windows wider than ±20°:

| Window | Centre | Half-gap | Verdict |
|---|---|---|---|
| 74.8 → 156.5 | **115.7** (green) | 40.9° | **Rejected.** Green *means "Normal"* in this palette, and the Normal timeline band is drawn behind the lines. A green diastolic line over a green Normal band is the same class of error the client rejected when they refused teal-on-the-Normal-chip. |
| 263.6 → 325.1 | **294.4** (violet) | 30.8° | **Selected.** No clinical meaning attached to violet; 27° from labs, 34° from incidents, 77° from systolic, **122° from the new accent**. |

*Greyscale derivation.* In light theme every plotted line must sit at relative luminance Y ≤ 0.2388 to clear 3:1 against `--color-mist`, which caps how far any line can separate from systolic (Y = 0.0413). Within the violet window the maximum achievable separation at palette-register saturation is 2.3–2.4:1. The chosen values were selected for **no greyscale regression in light and a 2× improvement in dark**:

| Pair (greyscale / luminance ratio) | Today | After | |
|---|---|---|---|
| light systolic ÷ diastolic | 2.22 | **2.32** | improved |
| light diastolic ÷ pulse | 1.17 | **1.23** | improved |
| light systolic ÷ pulse | 1.89 | 1.89 | unchanged — carried by the dashed pulse stroke |
| dark systolic ÷ diastolic | **1.12** | **2.24** | 2× improvement (this was the palette's worst number) |
| dark diastolic ÷ pulse | 1.29 | **1.96** | improved |
| dark systolic ÷ pulse | 1.14 | 1.14 | unchanged — carried by the dashed pulse stroke |

> **Correction to CONTEXT.** CONTEXT states "systolic and diastolic currently sit at only 1.89:1 luminance separation". Measured from `index.css`: light systolic ÷ diastolic is **2.22:1**; the 1.89:1 figure is light **systolic ÷ pulse** (which is what `CombinedTimeline.tsx`'s comment actually says, and what the dashed pulse stroke exists to solve). The genuinely broken pair was **dark** systolic ÷ diastolic at **1.12:1** — effectively identical in greyscale — and this phase fixes it.

Separation from the two violet-adjacent overlay colors:

| Pair | Hue Δ | Lightness Δ | Collision box (10°/10pp) |
|---|---|---|---|
| light diastolic `#AC40BF` vs labs `#6B4A9E` | 27.4° | 4.5pp | clears on hue, 2.7× margin |
| light diastolic vs incidents `#9C2E6E` | 34.1° | 10.4pp | clears on both |
| dark diastolic `#B055BE` vs labs `#C3A0E8` | 22.8° | 22.9pp | clears on both |
| dark diastolic vs incidents `#EFA0C9` | 36.9° | 24.3pp | clears on both |

Overlays also render as `◆ ▲ ■` glyph markers, never as a line, and the Show panel legend draws each series' exact stroke — so the non-colour signal is already in place.

`--line-pulse` stays `#9E4A24` / `#E3A07C`. The **pulse stroke stays dashed** — that is still the only thing separating pulse from systolic in greyscale, and `CombinedTimeline.test.tsx`'s dashed assertion must keep passing.

#### (2) The focus ring — brass confirmed, with one gap closed

**`--color-signal: #8A5A1E` (light) / `#D9A356` (dark)** — the client's candidate, confirmed. Rationale:

- Warm (hue 33) against a cool accent (hue 169) — **135° apart**, the largest separation available.
- Both pairs are **already asserted in `contrast.test.ts`** today under the `brass` keys, so no new derivation is needed: light 5.48:1 vs deck / 4.86:1 vs mist; dark 8.33:1 / 7.52:1.
- Retiring `#0F6E86` (hue 192.1) removes a token that would otherwise sit 23° from the accent — exactly the collapse DESIGN.md forbids.

Two constraints the implementation must honour:

- **The 2px `outline-offset` is load-bearing.** Focus ring against an accent fill is 1.24:1 (light) and 1.00:1 (dark) — luminance-identical in dark. The ring is only ever judged against the surface *behind* the control because the 2px offset exposes a band of deck/mist between fill and ring. Do not remove or zero the offset, and do not switch the ring to `box-shadow` (which has no offset semantics here).
- **Gap found and closed: the Command Bar's dark panel.** The Command Bar sits on `--color-panel` (`#101C2E` light / `#050A12` dark — non-inverting, always dark). Against `#101C2E`, the light focus ring is **2.90:1 — below the 3:1 floor**. This is *pre-existing*, not a regression (today's `#0F6E86` scores 2.93:1 there), but this spec closes it rather than inheriting it. Add a **non-inverting** focus token, mirroring the existing `--color-panel-text` precedent:

```css
/* declared identically in :root and .dark — non-inverting, like --color-panel-text */
--color-signal-on-panel: #D9A356;
```
```css
[data-surface="panel"] :focus-visible { outline-color: var(--color-signal-on-panel); }
```

Add `data-surface="panel"` to the Command Bar `<section>` in `App.tsx`. Scores 7.59:1 (light panel) / 8.81:1 (dark panel).

#### (3) The accent's two theme values

| | Light | Dark |
|---|---|---|
| `--color-accent` | **`#0D826C`** | **`#33C1A6`** |
| `--color-accent-text` | `#FFFFFF` | `#0A121F` |
| text-on-fill contrast | **4.74:1** | **8.33:1** |
| vs `--color-deck` | 4.41:1 | 8.33:1 |
| vs `--color-mist` | 3.91:1 | 7.51:1 |
| vs `--color-panel` (Send) | 3.61:1 | 8.80:1 |
| hue / sat / lightness | 168.7 / 81.8 / 28.0 | 168.6 / 58 / 48 |
| relative luminance | 0.1713 | **0.4160** |

The dark value was derived for **luminance parity with the brass it replaces** (`#D9A356`, Y = 0.4162 — a match to four decimals), so the dark theme's perceived accent weight does not change, and at the **same hue as the light accent** (168.6) so the accent has one identity across themes.

> **OPEN ITEM — conflict with the locked hex.** CONTEXT locks `--color-brass → #0E8C74`. Measured: `#FFFFFF` on `#0E8C74` is **4.18:1**, below the 4.5:1 AA floor that `contrast.test.ts` already asserts for the accent/accent-text pair. Every accent-filled text surface in the codebase is 20px/700 (verified: all 22 call sites use `text-label` or an explicit `fontSize: 20, fontWeight: 700`), which qualifies as WCAG *large* text and lowers the floor to 3:1 — so `#0E8C74` is not a WCAG failure. It *is* a gate failure and it spends the project's "high contrast is non-negotiable" budget on nothing.
>
> **Recommended resolution (assumed in every table in this file): `#0D826C`.** Identical hue (168.7) and saturation (81.8), lightness 30.2 → 28.0. Indistinguishable side by side; clears 4.5:1 at 4.74:1; needs no test relaxation.
>
> **Alternative, if the client wants the exact hex they chose:** keep `#0E8C74` and relax that single assertion from 4.5 to 3.0 with a comment citing the 20px/700 large-text exemption. Every other number in this spec is unaffected (`#0E8C74` scores 3.89:1 vs deck, 3.45:1 vs mist, 3.18:1 vs panel — all still clear 3:1).

### 4.4 Category chip selected state

Six BP categories plus three pulse categories (pulse reuses `--ref-bradycardia`, `--cat-normal`, `--cat-elevated` — `lib/palette.ts`, unchanged). Chips sit on the popover's `--color-mist` surface.

| | Rest | Selected |
|---|---|---|
| Fill | `var(--color-deck)` | `var(--cat-{n}-tint)` — **12% of the category hue over `--color-deck`** |
| Border | 2px solid `var(--color-depth)` | 2px solid `var(--cat-{n})` — the category's own hue, **never the accent** |
| Text | `var(--color-depth)`, 20px/700 | same |
| Category dot | 12px solid `var(--cat-{n})` | same — clinical identity is present in **both** states |
| Checkbox | native, 26px, `accent-color: var(--color-depth)` | checked (the tick is the non-colour signal) |
| Shape | `rounded-full`, `min-h-12` | same |

Three things change on selection — fill, border hue, and the tick — because the tint alone is weak (measured: a 12% tint is only 1.12–1.24:1 against the rest fill). The 3px ink `box-shadow` ring used today is **removed**: it existed because both states were solid clinical fills and could only differ by colour. `--cat-chip-text` is no longer used by FilterBar (it stays alive for ReadingsTable, CombinedTimeline band labels, ChartTooltip, AmPmComparison, CommandBar). `accent-color` on these checkboxes is `--color-depth`, **not** the accent — this is the exact teal-over-the-green-Normal-chip trap the client called out.

**How N is derived.** N counts **filter groups that differ from their shipped default**, not individual selections — "Filters · 7" after ticking seven chips is noise, and the detail already lives in the always-visible sentence. Maximum N is 4. Date is excluded (it owns its own trigger).

### 5.4 The D-20 live filter sentence — where it lives and why

**Immediately below the trigger row, in the content column, always rendered, never inside any popover.** 8px below the trigger row, 24px above the vitals strip. A `<div>` holding, stacked, three `<p aria-live="polite">` lines at `text-base` (18px/400), `var(--color-depth)`:

1. The filter sentence — `FilterBar`'s existing builder, verbatim: `"All data · All times of day · All categories · All pulse categories"`.
2. The Show sentence — `buildShowSentence(visibleDatasets)`, verbatim.
3. Conditionally, the existing note `"These datasets show on the Timeline. Switch back to see them."` when `chartView !== "timeline"`.

**This is a hard requirement, not a preference.** It is how the primary user — who cannot reliably open a popover and cannot see one he has not opened — knows what is applied. Burying any of these three lines inside the popover would mean an agent-applied filter change announces to nothing while the popover is closed, which is the normal state. All three are already `aria-live="polite"` regions today; this phase **relocates the markup and changes none of the strings**. The reason lines 2 and 3 are promoted alongside line 1: they are the same class of statement ("what is currently being shown"), they carry the same `aria-live` contract, and splitting them — one visible, one hidden — would be arbitrary.

> **Correction to CONTEXT.** CONTEXT says to build on "GuideOverlay's EXISTING focus-trap". `GuideOverlay` **has no focus trap** — its header comment states this explicitly and deliberately: "it has no dialog role, no modal attribute, and traps no focus: CommandBar (and the live mic session it drives) must stay fully reachable — including by Tab — while the guide is open (D-03/D-04)." The only focus trap in the codebase is in `LogoutConfirmDialog` (`Header.tsx`).
>
> **The filter popover and the nav panel must NOT trap focus, for exactly the reason the Guide doesn't:** a trap would lock a keyboard or switch-access user out of the mic and the Command Bar, which is the primary user's only reliable input. They are therefore **disclosures, not modals**: `role="group"` + `aria-label`, trigger `aria-expanded`/`aria-controls`, popover placed immediately after its trigger in DOM order so Tab flows trigger → contents → next control naturally. >
> `LogoutConfirmDialog` keeps its trap. It *is* a true modal — a destructive confirmation where trapping is the correct behaviour — and it is untouched by this phase. So the app ships **one disclosure pattern** (nav panel + filter popover, and `GuideOverlay` already behaves this way) and **one modal** (logout confirm). That satisfies CONTEXT's "ONE modal pattern, not two" intent more faithfully than literally adding a trap would.

**Dismissal:** `Escape`; the "Done" button; a `pointerdown` outside the popover (≥768px only). Outside-click is never the *only* route — "Done" is an explicit ≥48px target, which is what a voice or switch user needs.

**Sticky "Done" bar:** `sticky top-0`, right-aligned, `min-h-12`, mist fill, 2px depth border, `rounded-xl`, `text-label`. Copy is **"Done"**, not "Apply": filters apply immediately on change, so "Apply" would be a lie. The one real "Apply" — `DateRangePicker`'s, which commits a typed custom range — keeps its accent fill and keeps its name.

Extract the shared Escape + return-focus + delayed-unmount-fade behaviour into **one** hook, `frontend/src/hooks/useDismissable.ts`, consumed by the nav panel and the filter/dates popovers. CONTEXT asks for one pattern, and there are three consumers. `GuideOverlay` may adopt it later; **do not refactor `GuideOverlay` in this phase.**

**Responsive behaviour, and what wraps first:**

| Viewport | Content width | Layout | Row height |
|---|---|---|---|
| ≥1280px | 1072–1152px | 4 columns ≈ 260px each | **90px** |
| 1024–1279px | 720–880px | 4 columns ≈ 170px each | **90px** |

**The `min · max` line is the element that wraps first**, and only below 640px. Shrinking the type is forbidden. Two columns × two rows costs ~234px total — still a 2.5× reduction from today's 588px — and never requires horizontal scroll (No-Off-Screen Rule). A single column is explicitly rejected: 4 × 117px = 468px, barely better than today.

## 9. Known risks, measured

### 9.1 `categoryBarRightMargin` — no new narrowest case

CONTEXT flags the rail as "giving `categoryBarRightMargin` a new narrowest case". Measured arithmetic says otherwise:

| Viewport | Gutters | Rail | Chart container |
|---|---|---|---|
| 1440px (today) | 128 | — | 1280 − 128 = **1152** |
| 1440px (after) | 128 | 240 | 1200 − 128 = **1072** |
| 1024px (after, rail present) | 64 | 240 | 1024 − 240 − 64 = **720** |
| 1023px (after, rail is a panel) | 64 | 0 | **959** |
| **375px (today and after)** | 32 | 0 | **343** |

The rail is suppressed below 1024px, so it never reserves width at phone sizes. **The global narrowest container stays 343px and is unchanged by this phase.** `clampCategoryBarRightMargin` + `truncateLabelForWidth` already cover it (they were built for exactly that case in Phase 16's gap closure), and `chartData.test.ts`'s hardcoded 383/295/40 are outputs of `estimateChipWidth` — pure functions of label text and font size, not of container width — so they are **not** invalidated. Re-run the suite; do not pre-emptively retune `CHIP_CHAR_WIDTH_FACTOR`. Its own comment already says to bump it only against a real observed clip, never a guess.

### 9.2 Accent hue vs the Normal category

`--color-accent` at hue 168.6 sits **12.1°** from light `--cat-normal` (156.5) and **18.6°** from dark `--cat-normal` (150.0). Both clear DESIGN.md's 10° collision box, but 12.1° is the tightest margin in the palette. It is acceptable because the two never share an element: category chips are tinted in their own hue with a hue-matched border and a hue-matched dot, and the accent never touches a data surface. Recorded so a future palette edit knows the margin is thin.

### 9.3 Focus ring hue vs Stage 1 / pulse

`--color-signal` at hue 33.3 sits 9.4° from `--cat-stage1` (23.9) and 14.6° from `--line-pulse` (18.7). **This collision already exists in the shipped product** (brass is the accent today at the same hue) and is not worsened by demoting brass to the focus ring — the ring is transient, 3px, offset, and shaped. Not a blocker; recorded.
