# Phase 11 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

This is a continuation phase on an already-shipped, comprehensively documented,
hand-rolled Tailwind v4 system (`frontend/src/index.css`, header comment:
"Design-token system — 02-UI-SPEC.md locked palette"), matching Phase 6, 8, 9,
and 10's own UI-SPEC precedent. No `components.json` exists; none is
introduced here either — a shadcn gate would fork the visual language
mid-project for one overlay screen and one header button. **Zero new color
tokens, zero new typography roles.** The phase's real design work is the
overlay's *stacking/layering contract* (how a "full-screen overlay" can
visually dominate the screen while literally never touching the CommandBar's
mount point) — that is resolved explicitly below because 11-CONTEXT.md's
D-01–D-04 constrain it tightly but do not spell out the DOM/z-index
mechanics, and the executor needs zero ambiguity here to avoid accidentally
recreating a `useView`-style unmount.

11-CONTEXT.md already locked D-01 through D-13 (overlay mechanism, header
button placement/styling, voice open/close schema shape, TOC/section
structure, per-section fixed format). This document resolves every
"Claude's Discretion" item that has visual bearing (icon choice, ToC
styling) and adds the missing stacking/layering and copywriting detail so
planning and execution have one unambiguous source.

| Role | Value (light / dark) | Usage |
|------|------|-------|
| Dominant (60%) | `--color-foam` (`#F2F7F5` / `#0B1626`) | Guide overlay's own full-bleed background — **opaque**, not a dimmed backdrop (D-02: "no backdrop-click-to-close — a full-screen overlay has no backdrop to click"); matches every other full-page surface |
| Secondary (30%) | `--color-sky` (`#E2EDF2` / `#13233A`) | TOC jump-link chip surfaces; the sticky Close (X) button's surface; the CommandBar band that stays pinned above the guide (unchanged, inherited) |
| Accent (10%) | `--color-accent` (`#14213D` / `#8FC1D4`) | **No new use this phase.** The Guide header button is explicitly NOT accent-filled in either state (D-02: "mirrors the Theme/Voice Replies toggle's existing styling contract... bordered not accent-fill") — same treatment in open and closed state |
| Destructive | none — this project has no separate destructive/danger color | Not applicable; opening/closing a guide is non-destructive |

**Accent reserved-for list is unchanged by this phase** (still: Send button,
active/pressed date/AM-PM/category filter chips, active overlay toggle
fills, CommandBar's listening ring, Log-out confirm button, Phase 8's active
type-switcher segment/enabled Submit button). The Guide header button and
the guide's internal TOC/Close controls are deliberately excluded from this
list — styled identically to the Theme/Voice Replies toggles and the

**Zero new color tokens this phase.** State (guide open vs. closed) is
communicated entirely through `aria-pressed` + the overlay's presence/
absence — never through color, matching the project's non-color-only
convention with zero exceptions.

## Phase-Specific Component Contract

*(Additional detail beyond the standard template — the executor's primary visual reference.)*

### Overlay stacking/layering (resolves D-01–D-04's exact mechanics)

This is the load-bearing visual decision of the phase — get this wrong and
either the guide silently fails to satisfy GUIDE-03 (CommandBar becomes
unreachable) or it fails D-01 (guide isn't actually full-screen). The
contract:

1. **Nothing about `CommandBar`'s mount point changes when the guide opens.**
   The existing sky band (`<section className="bg-[var(--color-sky)]">`
   wrapping `CommandBar` + `AgentStatusBanner` in `App.tsx`'s `Dashboard`)
   stays exactly where it is in the render tree, unconditionally rendered,
   never wrapped in a conditional. It is promoted to a **raised stacking
   context** only while the guide is open (e.g. `relative z-[60]`, or
   `sticky top-0 z-[60]` if it isn't already effectively pinned) so it
   visually renders *above* the guide overlay layer without moving screen
   position, without unmounting, and without any prop/behavior change to
   `CommandBar` itself.
2. **The guide overlay is a new component** (e.g. `GuideOverlay.tsx`),
   rendered as an unconditional sibling placed AFTER the CommandBar band in
   the JSX (or portalled to the same stacking layer) — never wrapping,
   never replacing, never conditionally un-rendering any existing element.
   It is `position: fixed; inset: 0` with an **opaque** `--color-foam`
   background (D-02: no dimmed backdrop — a full-screen overlay has no
   backdrop) and a lower z-index than the CommandBar band's raised layer
   (e.g. `z-50` vs. the band's `z-[60]`), so it visually covers the header
   logo/title row and the entire `<main>` dashboard content underneath,
   while the CommandBar band punches through on top of it, unmoved.
3. **The guide's own scrollable content region** (ToC + sections + sticky
   Close button) gets top padding/margin equal to the CommandBar band's
   rendered height, so guide content visibly starts right below the pinned
   band — never underneath or overlapping it.
4. **No focus trap, no `aria-modal="true"`, no `role="dialog"`.** The guide
   region uses `role="region"` with `aria-label="Site guide"` (a landmark,
   not a modal) — because, unlike `LogoutConfirmDialog`, focus is
   deliberately NOT confined to the overlay: D-03 requires Chris to be able
   to Tab to or otherwise operate `CommandBar` (mic button, text input,
   Send) while the guide is open, so nothing outside the guide region may
   be marked `inert` or excluded from the tab order. Escape still closes
   the guide (D-02) as a plain keydown handler, not a modal-mandated one.
5. **Header's logo/title row and its Theme/Voice Replies/Upload/Add
   Record/Log out button group are visually covered** by the guide overlay
   when open (they sit at `z-0`, the guide sits at `z-50` above them) —
   this is expected and fine; none of those controls hold live session
   state the way `CommandBar` does, so covering them costs nothing.

### Header — new "Guide" button (D-02)

Placement: **immediately after the Voice Replies toggle and before
Upload/Add Record/Log out** in the header-right flex row — grouping the
three "site-wide display/output preference and help" toggles (Theme, Voice
Replies, Guide) together, ahead of the navigation/session controls.

```tsx
import { BookOpen } from "lucide-react";

// ...inside Header, in the header-right controls row, right after the
// existing Voice Replies toggle button:
<button
  type="button"
  onClick={() => setGuideOpen((open) => !open)}
  aria-pressed={guideOpen}
  className="flex min-h-12 items-center gap-2 rounded-lg border-2 border-[var(--color-ink)] bg-[var(--color-sky)] px-4 text-[20px] font-bold text-[var(--color-ink)]"
>
  <BookOpen aria-hidden="true" size={24} />
  Guide
</button>
```

No separate `aria-label` — the visible text is the accessible name (matches
the Theme/Voice Replies toggles' own convention). `size={24}` matches those
toggles' icon size exactly.

**Reachability across views (Claude's Discretion in 11-CONTEXT.md, planner's
call):** `Header` is already a single shared component mounted on all three
views (`Dashboard`, `UploadView`, `RecordsView`). This UI-SPEC's
recommendation is to add the "Guide" button to `Header` universally (all
three views) rather than dashboard-only, since it is one shared component
and the guide's own content is equally relevant from Upload/Records. On
Upload/Records there is no `CommandBar` band to pin above (none renders on
those views today), so the stacking contract above simplifies to just
steps 2–4 (opaque full-screen overlay, no raised-band special case). If
planning scopes it to dashboard-only instead, the button markup and guide
overlay contract above are unchanged — only the conditional around where
the button renders differs.

### Guide close control (D-02)

```tsx
import { X } from "lucide-react";

<button
  type="button"
  onClick={closeGuide}
  className="flex min-h-12 items-center gap-2 rounded-lg border-2 border-[var(--color-ink)] bg-[var(--color-sky)] px-6 text-[20px] font-bold text-[var(--color-ink)]"
>
  <X aria-hidden="true" size={24} />
  Close
</button>
```

Sticky near the top of the guide's own scrollable region (e.g. `sticky
top-0` within that region, its own small `--color-foam` backdrop strip so
scrolled content doesn't visually collide with it) — reachable without
scrolling back to the top, consistent with the project's "no drag,
hover-only, or precise-pointing interactions" constraint for a
motor-impaired primary user.

### Table of contents (D-11)

A wrapped row of chip-style jump links directly under the guide's `<h1>`,
styled like `OverlayToggle`'s inactive chip (never an active/pressed state
— ToC entries don't track "current section" in this phase):

```tsx
<nav aria-label="Jump to a section">
  <p className="text-[20px] font-bold text-[var(--color-ink)]">Jump to a section</p>
  <ul className="mt-2 flex flex-wrap gap-2">
    {SECTIONS.map((s) => (
      <li key={s.id}>
        <a
          href={`#${s.id}`}
          className="flex min-h-12 items-center rounded-lg border-2 border-[var(--color-ink)] bg-[var(--color-sky)] px-4 text-[20px] font-bold text-[var(--color-ink)]"
        >
          {s.label}
        </a>
      </li>
    ))}
  </ul>
</nav>
```

Plain anchor-link scroll (no JS smooth-scroll requirement, no active-section
tracking) — matches D-11's "fewest interactive states to build/test"
rationale exactly.

### Per-section fixed format (D-13)

Every content section (Command Bar, Filters, Charts, Overlay, Voice
Replies, Upload, Add a Record) follows, in order:

1. `<h2>` — Heading role (24px/700/1.2)
2. One Body-role paragraph: what it does
3. One Body-role paragraph, prefixed **"By click:"** (bold Label-weight
   lead-in inline, rest Body weight): how to use it by click
4. One Body-role paragraph, prefixed **"By voice:"** (same treatment) — how
   to use it by voice; **omitted entirely** for sections with no voice
   equivalent (Upload has none, per D-13's own example)

### "What Can I Say" section (D-08, D-09, D-10)

The LAST content section before "About This Guide." Renders grouped
category blocks (order fixed above in Copywriting Contract), each:

1. `<h3>` — Label role (20px/700/1.2): the category name
2. One canonical example phrase, quoted, Body-role text at bold weight
   (e.g. `<p className="text-lg font-bold">"show my pulse"</p>`)
3. The fixed "Similar phrasings work too — you don't need the exact words."
   note, Body-role regular weight

Content sources from `frontend/src/lib/voiceCommands.ts` (D-08's new shared
module) — this UI-SPEC fixes the category grouping and per-category
visual/copy shape; the exact phrase text per category is Claude's
Discretion (11-CONTEXT.md) exercised at execution time, constrained to stay
inside the categories and format fixed here.
