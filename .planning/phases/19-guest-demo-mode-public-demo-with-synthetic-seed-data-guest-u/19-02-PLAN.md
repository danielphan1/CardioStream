<objective>
Wire the `reject_if_demo` dependency (defined in Plan 19-01) onto the 4 mutating routes — `POST
/upload`, `POST /labs`, `POST /incidents`, `POST /procedures` — as a per-route dependency, never a
router-level one, and prove the whole guard (including auth-ordering) with a dedicated test file.

Purpose: this is D-03's actual enforcement point. `labs.py`/`incidents.py`/`procedures.py` each carry
BOTH a `GET` and a `POST` route inside one `APIRouter()`, so attaching `reject_if_demo` at
`app.main`'s router-include level (like `verify_token`) would incorrectly 403 the GET routes too —
the guard must attach directly to each `@router.post(...)` decorator instead (19-RESEARCH.md's
explicit per-route-not-router-level finding). The ordering test is not optional: FastAPI's
dependency-resolution order (router-level `verify_token` before route-decorator-level
`reject_if_demo`) is consistent with its DI model but not pinned in the public API contract, so this
plan writes an explicit regression test rather than trusting it silently (19-RESEARCH.md Assumption
A1).
Output: 4 one-line router changes + `backend/tests/test_demo_guard.py`, all green.
</objective>
