<objective>
Extend `Settings` with an optional `site_username` field, add a new independent `reject_if_demo`
dependency beside `verify_token`, extend `/auth` to require a matching username when configured, and
extend `/health` to report a `demo` boolean — all deriving from the SAME single field (per D-10's
carried-forward fail-closed/constant-time/never-logged discipline, and D-11's fail-first test
convention).

Purpose: this is the foundation every other plan in this phase builds on. `site_username` is the
single source of truth for "this is the guest demo deployment" — the write-route guard (Plan 19-02),
the frontend badge/hidden-UI/login-field (Plan 19-06), and the boot-time auto-seed (Plan 19-04) all
read this one value, never a second independently-set flag (per 19-CONTEXT.md's explicit anti-drift
warning). Per 19-RESEARCH.md's "Auth Mechanism Shape" finding, `reject_if_demo` deliberately does NOT
decode the Bearer token — D-01's separate-deployment isolation model means every valid token on a demo
deployment belongs to a guest by construction, so there is nothing to distinguish per-request.
Output: `Settings.site_username`, `reject_if_demo()`, an extended `/auth` compare, an extended
`/health` response, and full test coverage (extended `test_auth_upload.py` / `test_health.py`).
</objective>
