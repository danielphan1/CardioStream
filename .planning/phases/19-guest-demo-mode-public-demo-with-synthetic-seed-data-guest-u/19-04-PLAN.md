<objective>
Extend `app/seed.py` with an idempotent `seed_records()` for labs/incidents/procedures, MANDATORILY
wire it into `main()` behind a non-fatal try/except, and then gate a boot-time auto-seed invocation in
`start.sh` strictly behind `SITE_USERNAME` — removing the Railway-shell-access problem entirely for
the user standing up the second deployment (D-02's own framing), while also serving D-05's second
audience directly (anyone who clones the repo and runs `python -m app.seed` locally sees all four
data types populated in one command, not just readings).

Purpose: seeding is a one-time CLI action and guests are read-only (D-03), so per D-07 there is no
data-drift/reset problem to solve — "already populated" is simply a terminal state.
`resolve_source()`'s existing real-vs-sample fallback means a FRESH container with no gitignored
`data/` directory always seeds the synthetic sample — this is exactly why the auto-seed gate must be
strict: an ungated auto-seed would silently inject synthetic data into Chris's real production
database the moment its container restarts (19-RESEARCH.md Pitfall 1) — it never sets
`SITE_USERNAME`, so gating strictly on that one variable makes the dangerous path permanently dead
code there, with no second flag to remember to leave unset. Wiring `seed_records()` into `main()` is
NOT optional: `start.sh` only ever invokes `python -m app.seed` (i.e. `main()`), so if `main()` itself
never calls `seed_records()`, labs/incidents/procedures stay empty on both the hosted guest demo and
any local `python -m app.seed` run — exactly the "three of four record types are empty" outcome D-05
prohibits.
Output: `seed_records()` mandatorily wired into `main()`, `test_seed.py` (the first test file for
`app/seed.py` at all — including a subprocess test that runs the actual entry point end-to-end), an
extended `start.sh`, and an extended `.env.example`.
</objective>
