# Milestone v1.1: Polish & Records

**Status:** ✅ SHIPPED 2026-08-27
**Phases:** 6–12
**Total Plans:** 34

## Overview

Made the shipped v1.0 MVP more complete and more usable without needing the paid Claude API. Turned the previously-silent agent outage into an honest "assistant unavailable" state (Phase 6); gave the labs/incidents/procedures tables the schema already anticipated a real CRUD API (Phase 7) and accessible manual-entry forms to populate them (Phase 8); let Chris and caregivers toggle and overlay any combination of BP, pulse, labs, incidents, and procedures on one timeline, by voice or click (Phase 9); closed the hands-free loop with spoken confirmations via Web SpeechSynthesis (Phase 10); added a built-in, voice-navigable site guide covering every control and the full voice-command vocabulary (Phase 11); and modernized the visual theme sitewide with zero accessibility regression (Phase 12). Every phase kept the same discipline as v1.0: TDD where derivations/logic warranted it, code review before close, and a human verification pass for anything a DOM assertion can't judge (subjective visual calm, real-device voice/TTS behavior, cross-theme consistency).

## Phase Details

### Phase 6: Agent Availability (Liveness Detection)

**Goal**: Chris and caregivers always know — before speaking — whether the voice assistant will actually respond, replacing today's silent mislabeling of real outages as "didn't catch that."
**Depends on**: Nothing new (extends v1.0's existing `/agent` and `/health` infrastructure from Phase 3/5)
**Requirements**: LIVE-01, LIVE-02, LIVE-03, LIVE-04
**Success Criteria** (what must be TRUE):

  1. When the backend can't reach Claude (missing key, or every call failing), the UI shows a calm "assistant temporarily unavailable" message distinct from "didn't catch that," always paired with "manual controls still work."
  2. The dashboard checks assistant availability automatically when the page loads, so Chris knows before speaking whether the assistant will respond.
  3. Liveness checks never spend Claude API tokens and never share `/agent`'s rate limiter — checking status is free and never blocks real commands.
  4. A caregiver can tell "assistant is down" apart from "assistant didn't understand that" from the message text alone.

**Plans**: 3 plans (all complete)

- [x] 06-02-PLAN.md — Frontend liveness surface: agentStatus store, useHealth poll, AgentStatusBanner (LIVE-02, LIVE-03)
- [x] 06-03-PLAN.md — CommandBar/useVoiceCommand reactive wiring, closes switch-exhaustiveness gap (LIVE-01, D-07)

### Phase 9: Multi-Dataset Overlay & Filtering

**Goal**: Chris and caregivers can mix and match which data types they're looking at — by voice or click — and see them overlaid together on one timeline instead of living in separate silos.
**Depends on**: Phase 7 (GET endpoints); Phase 8 recommended complete first so overlay can be verified against real entered data, not just empty tables
**Requirements**: OVERLAY-03, OVERLAY-04, OVERLAY-05, OVERLAY-06
**Success Criteria** (what must be TRUE):

  1. Chris can toggle any combination of BP, pulse, labs, incidents, and procedures on or off by voice command.
  2. A caregiver can toggle the same combinations by click, with pressed/not-pressed state shown by word or icon, never color alone.
  3. Selected dataset types appear overlaid together on the BP Timeline and Pulse Trend charts (e.g. a hospital-stay marker plotted directly on the BP timeline).
  4. On the BP Categories and AM/PM charts, overlay controls visibly indicate they don't apply there, instead of silently doing nothing.
  5. Every overlaid event is also available in an accessible list/table, so keyboard and screen-reader users get full access regardless of chart-marker limits.

### Phase 10: Spoken Replies (TTS)

**Goal**: The dashboard speaks its confirmation aloud, closing the hands-free loop so Chris doesn't need to look at the screen to know a command worked.
**Depends on**: Phase 6 (needs the "unavailable" copy to speak), Phase 9 (needs the final overlay confirmation clause so spoken and visual replies don't diverge)
**Requirements**: TTS-01, TTS-02, TTS-03, TTS-04, TTS-05
**Success Criteria** (what must be TRUE):

  1. After a voice/agent command, the dashboard speaks the same confirmation text shown on screen; manual click/keyboard filter changes never trigger speech.
  2. Spoken replies are on by default; Chris or a caregiver can reach a mute/quiet toggle by voice or click, and the setting persists across sessions.
  3. Only one utterance ever plays at a time — a new confirmation cancels and replaces any reply still speaking.
  4. The mic pauses listening while the dashboard is speaking and resumes right after, so the assistant never mishears its own voice as a new command.
  5. Spoken replies work correctly on both Chrome/Edge and Safari/iOS, verified on a real device.

## Milestone Summary

**Key Decisions:**

- Continued phase numbering from v1.0 (ended Phase 5) — v1.1 runs Phase 6 through Phase 12, never restarting at 01.
- Overlay voice-toggle control (part of OVERLAY-03) folded into the main Phase 9 rather than split into a separate stretch phase as the research draft proposed — PROJECT.md's non-negotiable "every feature operable by voice" constraint and REQUIREMENTS.md's own OVERLAY-03 text placed it in v1.1 scope, not a deferrable stretch goal.
- Overlay accessibility mechanism: full-height `ReferenceLine` per event + separate accessible list, not a Scatter series bound into `accessibilityLayer` (Phase 9 design decision, `09-CONTEXT.md`).
- `toggle_dataset` agent schema is single-valued (one dataset token + explicit on/off per voice command), not list-typed (Phase 9 design decision).
- OVERLAY-03's toggle set reinterpreted as event-types-only (labs/incidents/procedures) — BP Timeline and Pulse Trend stay two separate hero charts, no new combined-metric chart.
- Liveness detection (Phase 6) built as a passive-only circuit breaker fed by real `/agent` traffic outcomes, not an active `count_tokens()` probe — zero added token cost.
- Visual Refresh (Phase 12) confirmed as its own phase despite zero grounding in any of the four v1.1 research files — closed with a dedicated lightweight research pass before execution rather than skipped.
- Each new agent command (`ToggleDataset` Phase 9, `ToggleSpeech` Phase 10, `ToggleGuide` Phase 11) added as its own closed-union `AgentOutput` member, structurally mirroring the prior precedent rather than inventing a new dispatch pattern each time.

**Issues Resolved:**

- Phase 8: 1 critical (async submit race causing silent data loss on mid-submit type-switch) + 3 warning code-review findings, all fixed same-session (`08-REVIEW-FIX.md`).
- Phase 9: 2 BLOCKER verification gaps (stale toggle-off overlay data, dark-mode WCAG contrast failure) closed by gap-closure plan 09-07 and independently re-verified.
- Phase 11: 1 critical (keyboard focus dropped to `<body>` on guide open) + 2 related warnings (jump-link scroll clearance, no focus restoration on close), all fixed same-session.
- Phase 11: two real bugs found and fixed during the phase's own manual-verification checkpoint (viewport-width content overlap; Tab-order gap into hidden content) — caught before code review even ran, via Claude-in-Chrome browser automation rather than deferring to the user.
- Phase 12: `min-h-12` grep-threshold miscalibration against a stale PATTERNS.md baseline — resolved by direct pre/post git-diff reconstruction proving zero accessibility-floor regression, rather than trusting the static count.
- 06-VERIFICATION.md's one human-judgment item ("calm, non-alarming" banner) — completed and passed in `06-HUMAN-UAT.md` on 2026-08-25 (status field on VERIFICATION.md itself was never flipped afterward; corrected at milestone close).

**Issues Deferred:**

- Activating the paid Claude API and agent-parsed voice/text data entry (AGENT-01, AGENT-02) — billing-only, no code change, deferred to v2 exactly as v1.0 left it.
- GUIDE-05 (voice-triggered contextual help), OVERLAY-07 (click/focus marker detail panel), LIVE-05 (distinguish "not configured" from "temporarily failing"), TTS-06 (speech rate/voice picker), GUIDE-06 (staged onboarding) — all explicitly acknowledged in REQUIREMENTS.md's v2 section, not roadmapped this milestone.
- Phase 10: 6 warning + 2 info code-review findings (`10-REVIEW.md`) — 0 critical, tracked for future follow-up rather than fixed this session.

**Technical Debt Incurred:**

- Phase 6 (`06-REVIEW.md` WR-03/WR-04, unresolved at milestone close): no `AbortSignal`/timeout on any `fetch()` call in `api/client.ts`, so a *hung* (not erroring) `/health` or `/agent` request defeats the liveness fail-safe; `useHealth()` also inherits TanStack Query's default 3x-retry backoff, delaying outage detection by several seconds. Neither blocks LIVE-01..04 as literally worded, but both undermine the phase's own robustness goal.
- Phase 8: CR-01's fix (guard against a stale mutation race clobbering `AddRecordPage` state on mid-submit type-switch) is concurrency-sensitive and could not be fully exercised by the existing synchronous-mock test suite — a manual spot-check (fill Lab form → submit → switch to Incident before the response resolves → confirm nothing is clobbered) was still pending at milestone close.
- Phase 10's 6 warning + 2 info code-review findings remain unresolved (see Issues Deferred above).
